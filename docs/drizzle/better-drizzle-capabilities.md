# better-drizzle capability inventory and merge plan

This inventory checks better-drizzle **0.3.0** against its source, with the pinned commit
[`f93f1b7aa528fe2db4cddc92a047e7a0ae710a0d`](https://github.com/almeidazs/better-drizzle/tree/f93f1b7aa528fe2db4cddc92a047e7a0ae710a0d).
The review covers the publication manifest, public entrypoints, every model/client method,
query and mutation compilers, relation executors, transactions, error handling and all plugins.
Capabilities remain in the design even without a current Raypx consumer. Upstream uses Apache-2.0; adapted code must retain provenance, copyright and the full license.

Status definitions: **Implemented** means an actual current `@raypx/drizzle` export;
**Planned** records extension work and does not make an API importable; **Native reuse** uses public Drizzle interfaces;
**Declared upstream only** means the pinned source has a type or preset without a corresponding complete implementation;
**Retained in inventory, outside the current implementation scope** preserves the source and semantics without scheduling a compatibility implementation.

The database scope is PostgreSQL, using postgres.js only (npm `postgres`) through
`drizzle-orm/postgres-js`. `pg`/node-postgres is unsupported; Bun SQL, PGlite and other drivers have no support plan.
The inventory preserves every upstream MySQL/SQLite entrypoint, capability, type and error code.
Their specific implementations are **retained in inventory, outside the current implementation scope**, even where upstream already implements them.
Unless stated otherwise, **Planned** covers shared and PostgreSQL/postgres.js capabilities only.

The [merge plan](merge-plan.md) defines the final public entrypoints and common semantics. `./query` denotes
the future query layer, containing client, mutation, predicate, ordering, pagination, prepared, lock,
transaction and raw-execution modules; `./relations` denotes the relation layer. These internal capabilities
do not each add a published entrypoint. PostgreSQL expressions use `./postgres`, and optional plugins use `./plugins/*`.
There is no plan for `./mysql`/`./sqlite`.
Only the upstream-entrypoint table in section 1 and the appendix describe upstream publication contracts.

Names such as `./client`, `./mutations`, `./prepared` and `./predicates` group capabilities;
they are not published subpaths. The [common merge plan](merge-plan.md) defines the final modules:
query capabilities use `./query`, and relations use `./relations`.

The upstream peer range, `drizzle-orm >=1.0.0-rc.4 <1.0.0-rc.5`, excludes the currently tested
`1.0.0-rc.5-5935859`. Plugins also have optional peers for Zod 3.25/4, ata-validator, ESLint 9 and
a TypeScript parser. The ORM facade depends on `db._.relations`, relation-object fields
`sourceColumns`/`targetColumns`/`through`/`throughTable`, and the junction field `column._.column`;
see [context.ts](https://github.com/almeidazs/better-drizzle/blob/f93f1b7aa528fe2db4cddc92a047e7a0ae710a0d/src/shared/client/context.ts)
and [factory.ts](https://github.com/almeidazs/better-drizzle/blob/f93f1b7aa528fe2db4cddc92a047e7a0ae710a0d/src/shared/client/factory.ts).
The merged implementation rebuilds explicit PostgreSQL table/relation descriptions using public APIs and consumer-supplied metadata.
Its execution core accepts PostgresJsDatabase/PostgresJsTransaction directly, without a multi-driver adapter.
Private client discovery is prohibited. Consumers create and manage postgres.js Sql/TransactionSql;
the library must not infer them from Drizzle sessions. Real PostgreSQL, postgres.js and declaration tests determine RC compatibility.

## 2. Model CRUD and batch writes

Sources: the [public delegate](https://github.com/almeidazs/better-drizzle/blob/f93f1b7aa528fe2db4cddc92a047e7a0ae710a0d/src/types/delegate.ts)
and [operations.ts](https://github.com/almeidazs/better-drizzle/blob/f93f1b7aa528fe2db4cddc92a047e7a0ae710a0d/src/shared/client/operations.ts).
Everything in this section is **planned** for `./query`. Only the explicit UPSERT expressions `excludedColumn(s)`
are implemented in `./postgres`; this does not imply an existing CRUD facade.

| Capability              | Actual upstream semantics                                                                                                                                        | Merge and extension constraints                                                                                                                                                             |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `findMany`              | Returns a row array; filtering, projection, relations, ordering, take/skip, cursor and locks                                                                     | Share the expression compiler and preserve native query composition                                                                                                                         |
| `findFirst` / `findOne` | Returns the first row or null; `findOne` has first-row semantics                                                                                                 | One canonical implementation, with aliases only in compatibility adapters                                                                                                                   |
| `findUnique`            | Requires where to identify one row through a primary or unique key; otherwise rejects                                                                            | Explicit unique-key descriptions; arbitrary where conditions must not be called unique                                                                                                      |
| `count` / `exists`      | Count returns the quantity; exists checks for a match using limit 1                                                                                              | Merge with drizzle-plus count and define precise numeric decoding                                                                                                                           |
| `create`                | Inserts and returns a record; optional select/include; skipDuplicates can return null                                                                            | Separate return types for duplicate skipping and ordinary creation                                                                                                                          |
| `createMany`            | Native multi-row insert returning `BatchResult { count, data? }`; supports chunking, skipDuplicates and projection                                               | Chunk by parameter budget; transaction policy must explicitly guarantee any cross-chunk atomicity                                                                                           |
| `update`                | Modifies at most one row; a limited-row path handles non-unique where; no match returns null; relation writes require exactly one match                          | Require unique identification by default; any first-match mode needs explicit ordering and selection semantics                                                                              |
| `updateMany`            | Applies the same data to all matching rows; optional scalar projection; missing or compiled-empty where returns count 0                                          | One shared same-value bulk operation; canonical entrypoints reject empty where by default; upstream no-op remains only in compatibility adapters; full-table writes require explicit opt-in |
| `updateEach`            | A `by` column, input rows and per-column callbacks; CASE assigns different values to each row; additional where, scalar select and `onEmpty: return/throw`       | Distinct from both upstream same-value `updateMany` APIs; drizzle-plus set callbacks, filter/limit and CTE target selection do not provide per-input-row values                             |
| `delete`                | Deletes at most one row and returns it or null; dialects without RETURNING read first                                                                            | Apply the same non-unique-identification rules as update and preserve transaction/concurrency semantics                                                                                     |
| `deleteMany`            | Deletes matches, returning count and optional data; empty where returns 0                                                                                        | Canonical entrypoints reject empty where by default; upstream no-op is a compatibility behavior, never an implicit delete-all                                                               |
| `upsert`                | `where/create/update`; uses native UPSERT when a unique conflict can be inferred, otherwise read-then-write; relation branches also read first                   | Require an explicit conflict target by default; inference is opt-in; document fallback as non-atomic and never switch silently                                                              |
| `upsertMany`            | Native batch UPSERT with explicit target; update supports key lists, object/SQL or callback excluded/current-column expressions; optional select/batchSize/where | Share implementation with drizzle-plus UPSERT; explicit targets, update keys and conflict-update predicates; no automatic overwrite of every column                                         |
| `skipDuplicates`        | Boolean or explicit target/targetWhere; PG/SQLite conflict-do-nothing; implementation checks MySQL insert-ignore restrictions                                    | Implement PostgreSQL ON CONFLICT DO NOTHING only; never swallow other constraint errors; retain MySQL/SQLite behavior in the inventory                                                      |
| `.throw(factory?)`      | Converts null from a single-row read/write to RESULT_NOT_FOUND or a consumer error                                                                               | Merge with drizzle-plus `orThrow` as explicit result unwrapping; current `first`/`inserted` are not full compatibility aliases                                                              |

`BatchResult.count` does not guarantee an exact affected-row count across dialects. Upstream MySQL `upsertMany`
returns the submitted input-row count, and some writes without RETURNING count before writing, introducing a concurrency window.
Canonical batch count means actual affected rows; input size, a pre-read match count or returned rows cannot substitute for it.
These differences remain recorded upstream facts; MySQL/SQLite are outside implementation. The PostgreSQL executor uses RETURNING
or verified postgres.js RowList.count for actual counts. Additional statistics need a separately designed API.
`updateEach` also requires validation of duplicate by keys, null keys, parameter limits and
CASE ordering; real transaction tests must cover concurrent updates and count discrepancies.

array indexes, empty and dynamic paths, and unknown schemas. Path arrays are the base interface; the dotted DSL is optional convenience.

Everything here is **planned/native reuse**. Current helpers do not manage connections or execute transactions.

| Capability               | Upstream scope                                                                                                                        | Common decision                                                                                                                                                  |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Row locks                | update/share/noKeyUpdate/keyShare; skipLocked/noWait are exclusive; PG table targeting; rejected on SQLite; optional transactionsOnly | `./query` reuses PostgreSQL native `.for`; test lock contention and connection ownership inside postgres.js transactions; preserve business claim/fence behavior |
| Query-shape restrictions | Restrictions on combining locks with include; normalized lock errors                                                                  | Explicit capability table; never silently drop a lock or split off an unlocked relation query                                                                    |
| Transactions             | Callback tx, nested savepoint, rollback(reason), afterCommit/afterRollback; explicit SQLite begin/savepoint path                      | `./query` directly composes PostgresJsDatabase.transaction and PostgresJsTransaction.transaction/savepoint; retain SQLite paths in the inventory only            |
| Transaction options      | isolationLevel, readOnly, timeoutMs, signal, meta/context, name/comment; unsupported options ignore/throw/warn                        | PostgreSQL isolation/read-only/local timeout implementation; reject unsupported options explicitly; AbortSignal does not imply postgres.js cancellation          |
| Retry                    | attempts, on(deadlock/serializationFailure/connectionError), delayMs(number/function)                                                 | Enable automatic retries explicitly; a connection error can leave commit outcome unknown, so non-idempotent callbacks cannot be retried safely by default        |
| Lifecycle callbacks      | Nested commit merges callbacks into the parent; run after the outermost commit; rollback clears the corresponding callbacks           | External effects occur only after commit; callback failure must not retry an already committed transaction                                                       |
| `$raw`                   | Tagged SQL/SQLWrapper; optional map, name/comment/meta/timeout/signal; returns rows                                                   | `./query`; planned. Reuse bound SQL; raw bypasses model CRUD transforms but has dedicated raw hooks                                                              |
| `$executeRaw`            | Also accepts bound SQL and returns `{rowsAffected?}`                                                                                  | Verify affected rows through postgres.js RowList.count/RETURNING; retain unknown when indeterminate, without multi-driver branches                               |
| `$rawUnsafe`             | Disabled by default; explicit allowUnsafe; string `?` placeholders plus parameters                                                    | Optional compatibility layer only; default public extensions accept Drizzle SQL; no naive handwritten placeholder substitution                                   |
| Raw global configuration | enabled/allowUnsafe/requireComment/timeoutMs/log/unsupportedOptions                                                                   | Consumers explicitly configure logging, cancellation and timeouts; sanitize log output first                                                                     |

Locks and transactions do not need Drizzle prototype changes. Bind transaction wrappers to public PostgresJsTransaction,
never the root db or another connection. Consumers own their Sql/TransactionSql lifecycle.
The library cannot observe automatic commits of an existing outer tx; afterCommit/cache invalidation needs explicit consumer notifications.
Test outermost commit, rollback, nested savepoints, hook order and connection ownership.

Diagnostics timeouts use PostgreSQL transaction-local statement_timeout/lock_timeout, then await
actual rollback and cleanup. Use public `.cancel()` only when explicitly holding a postgres.js PendingQuery.
Test 57014, cancellation races and connection recovery. Do not read private Drizzle sessions or present Promise timeouts
or AbortSignal guards as a guarantee that the database operation stops.

## 6. Context, scopes, hooks and plugin-author APIs

Sources: [scopes.ts](https://github.com/almeidazs/better-drizzle/blob/f93f1b7aa528fe2db4cddc92a047e7a0ae710a0d/src/shared/client/scopes.ts),
[plugins.ts](https://github.com/almeidazs/better-drizzle/blob/f93f1b7aa528fe2db4cddc92a047e7a0ae710a0d/src/types/plugins.ts),
the [plugin executor](https://github.com/almeidazs/better-drizzle/blob/f93f1b7aa528fe2db4cddc92a047e7a0ae710a0d/src/shared/client/plugins.ts)
and [hook types](https://github.com/almeidazs/better-drizzle/blob/f93f1b7aa528fe2db4cddc92a047e7a0ae710a0d/src/types/hooks.ts).
Everything is **planned** under `./query`/`./plugins/*`.

- Client: `better(db, options)`; access by table key; `repository(name)` accepts a TS key or a database table name.
  Extensions from `extends(object|factory)` rebind to clients derived through context/transaction and check key collisions.
- Context: `$withContext(meta)` clones and merges default metadata; per-call metadata overrides matching keys.
  Metadata is explicit context and does not itself establish authorization.
- Delegate: `$model {name,dbName,hasColumn}`, `$state`, `$withState` and
  `$withoutPlugins({keepScopes?})`. The latter removes scopes by default too, so this bypass requires explicit auditing.
- Scope: `PluginScopeDefinition` supports `key/model/root/missing/mismatch/bypass/session/rawSession`;
  models define `columns/immutable/nullable/stamp/upsert/where`. Applies to root tables, nested relations,
  relation filters, relation counts/ordering, mutations and conflict updates. Security scopes must be composed with AND;
  user filters cannot override them. Stamp writes and validates columns; immutable rejects changes to scope columns.
- Lifecycle: `beforeCreate/afterCreate`, `beforeUpdate/afterUpdate`,
  `beforeDelete/afterDelete`, `beforeQuery/afterQuery`, `onError`;
  `beforeRaw/afterRaw/onRawError`; `beforeTransaction/afterTransactionCommit/`
  `afterTransactionRollback/onTransactionError`. Context contains args/result/table/model/meta/
  tx/scope/state; never log the entire context by default.
- Plugin authors: `definePlugin`; `id/name/version/description/options`;
  `config.dialects/requires.columns`; `generated` declares generated columns and changes create-input optionality;
  `setup/transform/intercept/hooks/extendClient/extendModel/operationArgs/scope`;
  type-level model/client resolvers and strict hidden models. Interceptors follow plugin-array order, executing the outer layer first.
  Initialization validates duplicate ids, dialect, required columns/types, extension keys and operation-argument conflicts.
  Setup context exposes `addHook/addTransform/isColumnExists`, schema/dialect/models/plugin;
  client-extension context exposes `withScope`, and model-extension context exposes a bound delegate.
  Returning undefined from `PluginTransform` can skip an operation; interceptors can replace results or skip after hooks.
  The merge must constrain how such short circuits affect security checks and effects after commit.

The merged plugin pipeline has one execution model, without stacking drizzle-plus prototype hooks. Suggested order:
argument validation → mandatory scope → optional transform → execution → result validation → transaction commit → effects after commit.
Document whether each stage can rewrite arguments, short-circuit results or bypass other stages. Authentication/authorization scopes are separate
from optional caches and timestamp transforms; a generic bypass cannot remove security scopes.

## 12. Implementation order and acceptance

1. **Pure-function baseline**: column projections, explicit excluded expressions, strict PG error classification, result unwrapping, CASE-guarded JSON scalars,
   PG EXPLAIN construction and sanitized metrics. Mark implemented only when the actual export passes type and behavior tests.
2. **Expressions and batch writes**: scalar/JSONB/array predicates and mutations, safe ordering,
   batch UPSERT/updateEach. Merge equivalent drizzle-plus/better-drizzle capabilities on native builders.
3. **Pagination and diagnostics**: stable keyset semantics, offset-count consistency options, native prepared-read adapters,
   multiple-statement diagnostics and a postgres.js prepare/transaction/timeout matrix. Leave business token binding injectable.
4. **Explicit relations and optional clients**: public metadata descriptions, select/include/count, relation predicates and ordering,
   transactional connect/disconnect/set; then the typed facade. Private Drizzle fields must not be the default integration path.
5. **Scopes and plugins**: mandatory scope/tenant enforcement and transaction commit lifecycle first, followed by timestamp/uuid/soft-delete;
   cache, Zod, ATA, rules and static checks each require acceptance. Plugins can be consumed/disabled independently; bypassing security scopes needs separate authorization.
6. **Unimplemented upstream declarations and new extensions**: retain the full requirements for the 19 declared-only rules and aggregate/groupBy/nested create/connectOrCreate.
   These are future Toolkit additions, not existing upstream implementations.

Every phase requires clean-project artifact consumption, ESM/declaration tests, negative type assertions and real PG constraint/concurrency/
transaction/wrong-type JSON tests. Database coverage is PostgreSQL + postgres.js only; record PG17/18 feature gates
and the actual postgres.js/Drizzle peer versions. Keep MySQL/SQLite-specific capabilities in the inventory, outside implementation,
without a future multi-dialect/driver phase. Redis still requires real tests for its optional plugin.
Isolate plugin dependencies behind entrypoints and optional peers so base SQL helpers do not load validators, Redis or ESLint.
Document deliberate semantic changes with migration examples, especially updateMany/updateEach, batch counts, empty where,
scope bypasses, non-atomic upserts and diagnostic data. Independent package releases still require compatibility checks.
